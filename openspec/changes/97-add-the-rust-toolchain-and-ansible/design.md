# Design

## Decisions

- **Install the Rust toolchain as the `rust` tool of `mise.toml`: `rust = { version = "<release>", profile = "minimal", components = ["clippy", "rustfmt"] }`, locked with `mise lock` for `linux-x64` and `linux-arm64`.**: `mise.toml:1:The tools that Debian sid does not have` holds the pinned tools, and sid has rustc 1.99.1 while upstream has 1.100.0. The `minimal` profile with the two components gives each command of the issue in 623 MB; the `default` profile adds `rust-docs` and gives 1.3 GB and 66,000 files. The official Rust images also use the `minimal` profile.
- **Accept a `rust` entry of `mise.lock` with no URL and no checksum, and document it.**: `mise lock` writes only the version, `backend = "core:rust"` and the options, because the rust plugin of mise installs through rustup (`supports_lockfile_url` is false). rustup downloads the toolchain from the release server of Rust and checks each component against the sha256 of the channel manifest. `mise install --locked` installs the entry and exits 0, so `README.md:65` and `README.md:89` change for this tool.
- **Copy the toolchain folder that `mise exec -- rustc --print sysroot` prints, and link six commands from it in the last stage.**: `mise which cargo` prints `$CARGO_HOME/bin/cargo`, which is a link to the rustup proxy, and the toolchain is in `$RUSTUP_HOME/toolchains/<release>-<host>`. A copy of `$CARGO_HOME` holds only proxies: for a different home, `cargo --version` printed "rustup could not choose a version of cargo to run" and exited 1. The sysroot folder holds `bin/` and `lib/rustlib`, and `rustc` finds its standard library from its own path, so the links work. The command has no host triple, so the `Dockerfile` keeps no code for one platform.
- **Link `cargo`, `cargo-clippy`, `cargo-fmt`, `rustc`, `rustdoc` and `rustfmt`.**: `cargo` runs `rustdoc` from `PATH` for the doc tests of `cargo test` and for `cargo doc`; with no `rustdoc` link, `cargo test --doc` failed with "could not execute process `rustdoc ...` (never executed)". `cargo-clippy` finds `clippy-driver` beside its own file, so `clippy-driver` needs no link.
- **Add `gcc` and `libc6-dev` to the apt step.**: `rustc` links each program with `cc`: with no C compiler, `cargo test` failed with "error: linker `cc` not found". sid has `gcc` at its current release. With the two packages (32 packages, 244 MB), a user that is not root ran `cargo test`, `cargo clippy` and `cargo fmt --check` on a new crate with the toolchain folder read-only. The slim image of the official Rust images installs the same two packages.
- **Set no `CARGO_HOME` and no `RUSTUP_HOME` in the image.**: the linked commands are the real toolchain, not rustup proxies, so they need no `RUSTUP_HOME`. `cargo` keeps its registry and its cache in `~/.cargo` of the user, which each consumer can write; the toolchain folder stays read-only.
- **Teach `test/manifests.sh` that the `rust` key provides six commands, print one command name per line from each `case` arm, and add the six names of the `rust/bin` targets of the `ln -s` list to the copied set.**: `test/manifests.sh:22:echo "$command"` prints one line per tool key, and `test/manifests.sh:28:s/.*for command in//` cuts the joined `Dockerfile` at the last loop, so the Rust names come from the link list and not from a second loop.
- **Install `ansible-lint` as the fourth tool of the `python-tools` stage, from the hashed requirement file `python/ansible-lint.txt`.**: `Dockerfile:103:for tool in copier pre-commit semgrep; do` builds one virtual environment per tool with `Dockerfile:105:uv pip sync --require-hashes`, and `Dockerfile:153:ln -s ../lib/devtools/copier/bin/copier` links each command from its environment. The lock of ansible-lint 26.11.1 has a wheel of each package for each platform.
- **Accept the warning "PATH altered to include <environment>/bin" of ansible-lint.**: ansible-lint prints it on stderr and exits 0 when its command is a link into a virtual environment that holds `ansible`. It then runs the `ansible` commands of its own environment, which match the `ansible-core` that it imports. Its version check sends no request, because the INSTALLER of the distribution is `uv`.
- **Add `--lockfile requirements.txt:python/ansible-lint.txt` to the `osv-scanner scan source` step of the Image workflow, and handle a finding by the rule of `python/osv-scanner.toml`.**: The step names each Python lock file and is the gate of the image (`.github/workflows/image.yml:176`). A finding with a released fix gets a higher pin; a finding that no release fixes gets one narrow ignore with a reason, a tracking issue and an end date 3 days ahead, as the header of `python/osv-scanner.toml` says.
- **Add the Rust version checks to the mise.lock block of `test/tools.sh` in alphabetical order, `gcc --version` to the apt block, and `ansible-lint --version` before `copier`; then build and test a new crate offline.**: The script groups each tool by its installer (`test/tools.sh:61:The tools of mise.lock`), and runs in the image with no network (`test/tools.Dockerfile:11`). A version check does not prove the linker or `rustdoc`; `cargo test` of a new library crate runs `rustc`, the linker and the doc tests of `rustdoc`.
- **Change the message of `test/manifests.sh` to name the commands of the copy loop and of the links, so that the printed number matches the set that the check reads.**: `test/manifests.sh:42:tools of mise.toml.` prints one number for a set that now holds a tool with six commands.
- **Plan no code for the release.**: release-please opens the release pull request, the release workflow turns on auto-merge, and the tag starts `image.yml`, which publishes the image (`README.md:173` to `README.md:175`). The `RUNNER_TOOLS` rows belong to the other repository.
- **Carry no spec delta: the change is the image build, its shell tests, its workflow and its documents, and the repository holds no `src/` package and no living spec whose requirement could describe this behavior.**: `test/manifests.sh:2:Checks that the copy loop of the Dockerfile and the tools of mise.toml name the same commands.` and `test/tools.sh:2:Runs each tool of the image once and prints its version.` are the proofs that this repository uses.

## Rejected alternatives

- **Install the Rust toolchain from the apt packages rustc, cargo, rust-clippy and rustfmt.**: The rule of `README.md:74` uses apt only where sid is current, and on 2026-11-27 sid had rustc and cargo 1.99.1 while upstream had 1.100.0.
- **Install the toolchain with the rustup shell script in the `Dockerfile`.**: The image installs each binary tool from `mise.toml` (`Dockerfile:33:mise install --locked`), and `test/manifests.sh:11` reads only the keys of `mise.toml`, so a second installer would add a tool that the check does not see and that Renovate's mise manager does not move.
- **Copy the two levels above `mise which cargo`.**: That folder is `$CARGO_HOME`, 21 MB of rustup proxies with no toolchain. For a different home, the linked `cargo --version` printed "rustup could not choose a version of cargo to run" and exited 1.
- **Ship rustup and its proxies with `RUSTUP_HOME` and `CARGO_HOME` set in the image, as the official Rust images do.**: The official slim image makes the two homes writable by all users (`chmod -R a+w`), which a read-only root refuses, and a proxy chooses the toolchain that a `rust-toolchain.toml` of a repository names, such as `channel = "stable"`, which the image does not hold. The linked toolchain needs no writable folder of the image.
- **Use the `default` profile of rustup, which mise uses when `mise.toml` names no profile.**: It adds `rust-docs`: the toolchain folder grows from 623 MB to 1.3 GB and 66,000 files, and the runner image of devops-cli (6.05 GB, limit 7,000,000,000 bytes) builds FROM this image.
- **Rely on the `rust-lld` of the toolchain and add no C compiler.**: `rustc` calls `cc` as the linker driver: `cargo test` failed with "error: linker `cc` not found".
- **Copy only the Rust commands to `/out/bin` with the other mise tools.**: `Dockerfile:38:install -m 0755 "$(mise which "$command")" "/out/bin/$command"` copies one file per command, and that file is a rustup proxy; a copied `rustc` of the toolchain would also hold no `lib/rustlib`.
- **Add a second `for command in` loop to the `Dockerfile` for the Rust commands.**: `test/manifests.sh:28:s/.*for command in//` cuts the joined text at the last loop, so the check would see only the second loop's commands and report the 27 other commands as missing.
- **Install `ansible-lint` from the apt package of sid.**: On 2026-11-27 sid had ansible-lint 26.4.0 while upstream had 26.11.1, and the rule of `README.md:74` uses apt only where sid is current.
- **Install `ansible-lint` with `uv tool install`, as the proposed design of the issue says.**: `Dockerfile:103:for tool in copier pre-commit semgrep; do` and `Dockerfile:105:uv pip sync --require-hashes` show one virtual environment per Python tool from a hashed requirement file, and `README.md:93:Each Python tool has a virtual environment of its own` states the layout. A uv tool environment would stop the PATH warning of ansible-lint, but it would install a second way.
- **Install `ansible-lint` with pip into the system Python.**: `Dockerfile:105:uv pip sync --require-hashes` shows that each Python tool comes from a hashed requirement file of `python/`, and pip would add a second install path with no hash.
- **Install `ansible-lint` with the pipx backend of mise.**: `Dockerfile:100:--mount=type=bind,source=python,target=/tmp/python` shows that the Python tools come from the `python/` folder, and `README.md:84:pip-compile` names the one manager that updates them.
- **Add one new block for all the new commands to `test/tools.sh`.**: `test/tools.sh:61:The tools of mise.lock` and `test/tools.sh:2:Runs each tool of the image once and prints its version.` show that the script groups each tool by its installer, and a mixed block hides which installer provides each tool.
- **Add only version checks for the Rust commands.**: `cargo --version` passed in a folder with no linker and no `rustdoc`, where `cargo test` failed; only a build and a test of a crate prove them.
- **Add a Python test that reads the `Dockerfile` and `test/tools.sh` and asserts the new commands.**: The repository holds no `src/` folder and no `tests/` folder, and `test/manifests.sh:2:Checks that the copy loop of the Dockerfile and the tools of mise.toml name the same commands.` shows that the repository proves the image with a shell check and the live image build.
- **Make the Trivy image scan the gate that proves the new tools safe, as the proposed design of the issue says.**: `.github/workflows/image.yml:206:The scan is report-only` and `.github/workflows/image.yml:210:The gate stays on the lock files` show that only the osv-scanner step fails the job on a finding.
- **Add a capability with the requirements of the refine block.**: The repository holds no `src/` folder, no `tests/` folder and no living spec, so every added scenario would stand with no behavior task; `test/manifests.sh` and `test/tools.sh` are the proofs that this repository uses.
